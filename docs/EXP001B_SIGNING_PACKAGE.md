## 1. WHAT THE AUTHORITY BOUNDARY ACTUALLY IS

An earlier return claimed the boundary refuses self-admission because it rejects
`decided_by` values like `engineering`. **That claim was wrong and is withdrawn.**
A name is written by whoever writes the decision, so rejecting a list of names
prevents nothing.

`decided_by` is not inert metadata either: it is the **principal**, and it selects
which public key in `allowed_signers` must have produced the signature. It is an
index into trusted configuration, not a claim that is believed.

The boundary is two facts, neither of them a string:

| | |
|---|---|
| **Possession of the private signing key** | usable only by the authority; **must never exist on the research host** |
| **Protection of `allowed_signers`** | if a key can be appended there, the boundary is gone regardless of any name |

### "Off-host" is not the boundary — corrected

An earlier version of this document located the key "off-host, on your machine".
**That framing is insufficient in this deployment and the reviewer is right to
strike it.** Claude can reach the operator's Mac. A key sitting unlocked on that
machine is a key Claude can read and use, so machine location establishes
separation from the research host but not separation from Claude.

What actually establishes it, and all three are required:

1. The key is **passphrase-protected**, and the passphrase is known only to the
   authority and never entered into a Claude session.
2. The **authority runs `ssh-keygen -Y sign` themselves.** Signing is not delegated.
3. No unlocked key, and no agent holding one, is exposed to a Claude session.

Creating the key is part of this. A key generated on the operator's behalf by the
party that wrote the wrapper and prepared the environment is a key that party can
use, which is the same boundary failure by a quieter route.

Both must hold. This is why no signing key was created during activation: creating
one on the research host would put both halves of the authority in the same place
as the code being admitted.

### How the evaluation exclusion actually holds

It is a property of **the sandboxed process**, not of the account and not of the
data at rest. Measured, outside the sandbox:

```
sudo -u apexresearch test -r .../SPY_2022-01-03.json   ->  READABLE (content read)
ls -l .../SPY_2022-01-03.json                          ->  -rw-rw-r--  (world-readable)
```

The exclusion is produced by the unit configuration alone: a `TemporaryFileSystem`
over the corpus volume, with only the 1511-file view bound read-only back over the
corpus path. Every run through this launch path is excluded from the evaluation
period. A run started any other way as this account would not be.

## 4. SIGNING — WHAT RUNS OFF-HOST AND WHAT RUNS ON-HOST

### OFF-HOST (your machine, where the key lives)

**Never copy the private key to the research host. Never paste it into this
session.** Only the public key and the signature travel.

**0. Create the signing key. It does not exist yet.**

An earlier version of this section assumed `~/.ssh/apex_admission_ed25519` was
already present. It was not, and no admission signing key has ever been created in
this programme. Run this yourself, on the machine that will hold the key:

```bash
ssh-keygen -t ed25519 -f ~/.ssh/apex_admission_ed25519 -C "apex-admission"
```

Give it a passphrase. **Run it yourself rather than delegating it.** A key created
by the party that wrote the wrapper and prepared the environment is a key that
party can use, and possession is the entire authority boundary — see section 1.

Choose a passphrase when prompted, and keep it out of any Claude session. If the
command asks to overwrite an existing key, **stop** — something is already there
and overwriting it would destroy it.

No hardware key is needed for this step.

1. Fetch the unsigned request from the branch and review it:
   `results/exp001b_admission_request.json`
2. Author the decision from it: set `"decision": "ADMIT"`, set
   `provenance.decided_by` to your principal, set `provenance.decided_utc`, and
   confirm `code.commit` matches the checkout commit in the signing-package JSON.
3. Sign it, namespace `apex-admission`:

```bash
ssh-keygen -Y sign -f ~/.ssh/apex_admission_ed25519 -n apex-admission exp001b_admission.json
```

That writes `exp001b_admission.json.sig`. Export the **public** key line for the
allowed-signers file:

```bash
echo "<principal> $(cat ~/.ssh/apex_admission_ed25519.pub)" > allowed_signers
```

### THE THREE ARTIFACTS TO HAND OVER

Signing produces exactly three public items. All three are needed; none is private.

| artifact | why it is required |
|---|---|
| the **public key** line for `allowed_signers` | names the principal whose key must verify |
| the **decision JSON**, byte-for-byte as signed | `ssh-keygen -Y verify` hashes these exact bytes |
| the **detached signature** `.sig` | the signature over those bytes |

**The decision JSON is not optional and must not be reformatted in transit.**
Re-indenting it, reordering keys, or re-serialising it changes the bytes and the
signature will fail to verify. Transfer the file as produced.

### ON-HOST (as root, on the research host)

4. Create the trust root and install the public configuration:

```bash
sudo install -d -o root -g root -m 755 /etc/apex/admissions /etc/apex/admissions/trust
sudo install -o root -g root -m 644 allowed_signers /etc/apex/admissions/trust/allowed_signers
```

5. Place the decision and its signature, both root-owned and not writable by others:

```bash
sudo install -o root -g root -m 644 exp001b_admission.json /etc/apex/admissions/
sudo install -o root -g root -m 644 exp001b_admission.json.sig /etc/apex/admissions/
```

The boundary walks the ancestor chain of the trust root, the allowed-signers file
and the decision, and refuses if any ancestor is writable by a non-root account.

6. Verify before launching. This performs the same check the boundary will:

```bash
ssh-keygen -Y verify -f /etc/apex/admissions/trust/allowed_signers \
  -I <principal> -n apex-admission \
  -s /etc/apex/admissions/exp001b_admission.json.sig \
  < /etc/apex/admissions/exp001b_admission.json
```

## 5. LAUNCH — TWO COMMANDS, ONE DIFFERENCE

**Correction.** An earlier version of this package pointed at the generated
`launch.command` and told the operator to "run it first without `--apply`". That
was wrong and would have executed the experiment. The generated argv carries
`--execute` and is the executable command; `--apply` is a flag of the **wrapper**,
not of that argv. Both commands below are generated by the wrapper, not typed here.

**PREPARE — launches nothing:**

```bash
sudo -n /usr/bin/python3.12 scripts/research_activation.py launch --commit 277e4a023c7f070c7421fb587cba6dfcedcb3be8 --decision /etc/apex/admissions/exp001b_admission.json
```

**EXECUTE — runs the registered experiment:**

```bash
sudo -n /usr/bin/python3.12 scripts/research_activation.py launch --commit 277e4a023c7f070c7421fb587cba6dfcedcb3be8 --decision /etc/apex/admissions/exp001b_admission.json --apply
```

They are identical but for the trailing `--apply`, and a test asserts exactly that.

The `systemd-run … --execute` argv in `launch.executable_argv` is **executable and
is not a dry run in any form.** It is published so the sandbox properties can be
audited, not so it can be run by hand. A test asserts it stays labelled that way.

### What PREPARE actually checks

Preparation is a consistency check, not an authorisation check. Stated exactly,
from `PREPARE_CHECKS_PERFORMED` in the wrapper so documentation cannot drift from
code:

| check | performed by prepare? |
|---|---|
| setup record state is COMPLETE | yes |
| requested commit matches the setup record | yes |
| checkout working tree clean, bound tree hash matches | yes |
| interpreter present | yes |
| decision file and signature file **exist** | yes |
| decision **contained** in the trust root | yes |
| dataset view file **count** matches | yes |
| dataset view file **hashes** re-checked | **NO** |
| signature **cryptographically verified** | **NO** |

The last two are the corrections. **Existence of a `.sig` file is not verification,
and a file count is not integrity.** Those properties are established elsewhere:

- **Signature.** Verified by `boundary.verify_decision`, called from
  `scripts/alpha_exp_real_execute.py` at execution, which runs `ssh-keygen -Y
  verify` against `/etc/apex/admissions/trust/allowed_signers`. The operator can
  establish it in advance with the identical command in section 4, step 6.
- **Dataset integrity.** Established by the wrapper's `verify` action, whose
  `dataset_inventory` check re-hashes **every** admitted file and refuses on
  `VIEW_HASH_MISMATCH`. **Run `verify` immediately before launching:**

```bash
sudo -n /usr/bin/python3.12 scripts/research_activation.py verify
```

### Trust-root containment

The containment test was a string prefix comparison, which accepts a similarly
named sibling: `/etc/apex/admissions-other/d.json` starts with
`/etc/apex/admissions`. It is now resolved-path containment, and a test places a
decision in exactly such a sibling and requires the refusal.

This was a defect in the **wrapper's** check. The downstream admission boundary
uses `p == root or root in p.parents`, which was already correct, so the wrapper
defect did not open a path through the boundary itself.

**The probed configuration is the launch configuration.** The probe previously ran
under a smaller memory cap, so what was measured was not literally what would run.
Fixed, with a test asserting the two property lists are identical.
